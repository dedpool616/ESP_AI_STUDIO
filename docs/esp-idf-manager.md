# ESP-IDF Manager: обнаружение окружения

Первый этап доступен в разделе **ESP-IDF Manager** бокового меню.

Он обнаруживает SDK через `IDF_PATH`, конфигурации Espressif EIM (`eim_idf.json`)
и старого установщика (`idf-env.json`), а также ограниченный поиск в стандартных
каталогах. Полного сканирования дисков нет.

Python выбранной установки имеет приоритет над системным Python. CMake и Ninja
ищутся также в каталогах инструментов Espressif, даже если их нет в PATH.
Показываются фактические пути, версии, источники и ошибки каждого инструмента.

Кнопка **Указать папку ESP-IDF** выбирает корень SDK, а не папку пользовательского
проекта. Выбор сохраняется отдельно от сессий редактора в
`userData/environment-settings.json`. Пункт **Автоматический поиск** сбрасывает
ручной выбор. Некорректная папка или отмена выбора сохраняет предыдущие настройки.

Проверка версий запускает известные исполняемые файлы с фиксированным аргументом
`--version`, без shell, с таймаутом 3 секунды и скрытым окном. Для компилятора
дополнительно используется `-dumpmachine`. Его версия и архитектура сверяются с
выбранной платой и поддерживаемыми версиями из `tools/tools.json` этого SDK.

Основные Python-пакеты проверяются штатным `tools/check_python_dependencies.py`
через найденный Python с флагом `-B`, файлом `requirements.core.txt` и локальным
constraints-файлом соответствующей версии SDK. Таймаут — 15 секунд. Если файл
ограничений отсутствует, результат остаётся частичным: скачивания не выполняются.
Полный PATH из диагностического вывода скрипта не передаётся в интерфейс.

Проверки используют копию окружения дочерних процессов: пути выбранных
инструментов, IDF_PATH, IDF_TOOLS_PATH и IDF_TARGET. Системный PATH и окружение
родительского процесса не меняются. Activation/export-скрипты не выполняются,
байткод Python не записывается, установка компонентов и сборка отсутствуют.

Плата для проверки берётся из проекта, если задана поддерживаемая плата, иначе
используется ESP32-S3. Можно проверить ESP32, ESP32-S2/S3, ESP32-C3/C6. Выбор
диагностической платы не изменяет метаданные или sdkconfig проекта.

Совместимость CMake и Ninja также сверяется с tools.json. Пройденные проверки
подтверждают только проверенные зависимости. Следующие этапы — дополнительные
инструменты (например, ULP), подключение процесса сборки и пробная сборка.

## Проверки

```powershell
node --test tests/*.test.cjs
npm.cmd run typecheck
node node_modules/eslint/bin/eslint.js .
npm.cmd run build
```

В настоящем приложении:

1. Открыть ESP-IDF Manager и дождаться отчёта. Проверить SDK, Python, Git, CMake,
   Ninja и фактические пути.
2. Нажать «Проверить окружение» повторно: страница остаётся отзывчивой.
3. Выбрать SDK из списка, перезапустить приложение и проверить сохранённый выбор.
4. В выборе папки нажать отмену: предыдущий отчёт и выбор сохраняются.
5. Указать обычную папку проекта: появляется ошибка внутри страницы, старый выбор
   сохраняется. Затем указать папку SDK и убедиться, что выбор работает.
6. Переключить режим на автоматический поиск.
7. Перейти в Code Editor и обратно: редактор сохраняет свои вкладки и правки.
8. Проверить выбранную плату и карточки Python-пакетов, основного компилятора,
   совместимости CMake и Ninja. Для текущей установки ESP-IDF 6.1 и ESP32-S3
   они должны показывать успешную проверку.
9. Выбрать другую плату диагностики, дождаться нового отчёта и проверить, что
   заголовок результата соответствует плате. SDK и файлы проекта не меняются.
